# 初回訳の表示時間（2026-11）

文字の多い画面を範囲翻訳したとき、最初の訳が出るまでの時間を短くした変更の方法と計測結果。
再現用のスクリプトとデータは [`bench/latency/`](../bench/latency/) にある。

## 結論

- 内蔵の翻訳モデル（PLaMo 3 Translate）では、選択範囲を**分割して順に翻訳**する。
  先頭は小さく（`FIRST_PART`）、以降は大きく（`LATER_PART`）まとめる。
- 各リクエストには、**それまでの原文と訳文を翻訳履歴**として渡す。
  先頭部分には**後続の原文を参照用の文脈**（`context`）として渡す。
  どちらも PLaMo 3 Translate が公式に対応する PFML3 の要素である。
- その結果、最初の訳が出るまでの時間は長文記事で **3.2 秒 → 0.5 秒**、
  中程度の画面でも約半分になった。翻訳品質（chrF）は一括翻訳と同等。全体の所要時間はほぼ同じ。
- 1回のリクエストが短くなるため、大きな範囲でも制限時間（15 秒）を超えなくなった。
  一括翻訳では長文記事の翻訳に約 38 秒かかり、制限時間を超えて失敗していた。
- 他の翻訳プロバイダー（Ollama・DeepL など）は文脈を受け取らないため、従来どおり一括で翻訳する。

## 仕組み

`src-tauri/src/translate_plan.rs` が分割を決め、`Pipeline::translate_capture_with_progress` が順に翻訳する。

1. 翻訳が必要なブロックを読み順に並べ、コスト（ASCII 1、それ以外 3。トークン数の近似）で区切る。
   先頭は 160、以降は 600 まで。ブロックは途中で切らない。
2. 2番目以降の部分の原文を、先頭から 200 まで参照文脈にする。
   同じ参照文脈を全リクエストの先頭に置くので、プロンプトの先頭が毎回一致する。
3. *n* 番目のリクエストは「参照文脈＋1〜*n*−1 番目の原文と訳文＋*n* 番目の原文」。
   前回のプロンプトと出力がそのまま先頭に来るため、エンジンの KV キャッシュが再利用され、
   新しい原文だけを読めばよい。履歴は 6000（約1500トークン）を超えたら古い順に捨てる。
4. 段落数が合わない部分だけを1ブロックずつ翻訳し直す。その際も履歴と参照文脈を渡すので、
   「Save」「Light」のような短いラベルも文脈付きで訳される（従来は文脈なしで全ブロックを翻訳し直していた）。
5. 各リクエストの前に `moonlens://selector-progress` で「完了したブロック」と「次に流れてくるブロック」を
   選択画面へ通知し、ストリーミング中の訳文を正しい位置に表示する。

## 方法

- **実行環境**: クラウドの x86 CPU 4コア（GPU なし）。llama.cpp（`llama-cpp-python` 0.3.37）、
  `n_threads=4`、PLaMo 3 Translate 2B Q4_K_M、temperature 0。
- **データ**: `bench/latency/screens.json`。OCR 後のブロック列を想定した5画面
  （ニュース記事・設定画面・ゲームのクエスト画面・日本語の手順書・長文記事）。長文記事以外は参照訳付き。
- **比較**: `whole`（従来。全ブロックを空行で連結して1回で翻訳）と `chunked_ctx`（今回の方式）。
  調査用に `chunked`（参照文脈なし）も計測した。
- **指標**: 最初のトークンが出るまで、最初のブロックが完成するまで、全体の所要時間、chrF（英→日は文字 chrF、日→英は chrF++）。

## 結果

| 画面 | 方式 | 最初のトークン | 最初のブロック完成 | 全体 | chrF |
| --- | --- | ---: | ---: | ---: | ---: |
| ニュース記事（英→日、10ブロック） | 一括 | 1.45 s | 2.26 s | 18.7 s | 60.4 |
| | 分割 | **0.74 s** | **1.56 s** | 19.6 s | 61.3 |
| 設定画面（英→日、19ブロック） | 一括 | 0.77 s | 0.95 s | 8.7 s | 85.5 |
| | 分割 | 0.77 s | 0.94 s | 8.5 s | 83.7 |
| クエスト画面（英→日、12ブロック） | 一括 | 0.95 s | 1.20 s | 9.6 s | 46.6 |
| | 分割 | **0.56 s** | **0.82 s** | 10.0 s | 46.8 |
| 手順書（日→英、10ブロック） | 一括 | 1.42 s | 1.68 s | 11.4 s | 79.6 |
| | 分割 | **0.67 s** | **0.95 s** | 11.9 s | 78.5 |
| 長文記事（英→日、13ブロック） | 一括 | 3.17 s | 4.08 s | 37.8 s | — |
| | 分割 | **0.54 s** | **1.18 s** | 38.0 s | — |

- 一括翻訳の待ち時間は原文の長さに比例して伸びるが、分割では画面の大きさによらず 0.5〜0.8 秒で最初の訳が出る。
  設定画面は先頭の短いラベル群がそのまま最初の部分に収まるため差が出ない。
- chrF の差（±2 以内）は言い換えの違いによるもので、目視では同等。
  「マーケット通り」「起動時に前回のワークスペースを開く」（チェックボックスのラベル）など、分割の方が参照訳に近い箇所もある。

### アプリ本体のエンジンでの確認

同じ5画面を、アプリの翻訳パイプラインと内蔵 llama.cpp エンジンで計測した
（`cargo test --test translate_in_parts -- --ignored --nocapture`、デバッグビルド、同じ CPU）。
一括は `MOONLENS_TEST_WHOLE=1` で従来の動作にしたもの。

| 画面 | 最初のトークン（一括 → 分割） | 全体（一括 → 分割） |
| --- | ---: | ---: |
| ニュース記事 | 2.73 s → **1.07 s** | 19.3 s → 19.6 s |
| 設定画面 | 1.62 s → **1.22 s** | 8.5 s → 8.7 s |
| クエスト画面 | 1.71 s → **0.88 s** | 9.2 s → 9.5 s |
| 手順書 | 2.06 s → **1.00 s** | 11.2 s → 11.6 s |
| 長文記事 | 5.49 s → **0.87 s** | 38.2 s → 37.7 s |

デバッグビルドのため絶対値は Python より遅いが、分割では画面の大きさによらず約 1 秒で最初の訳が出る。
2回目以降のリクエストでは、前回までのプロンプトと出力の KV キャッシュがそのまま使われる
（例：長文記事の5回目は 510 トークン中 430 トークンを再利用）。

### 参照文脈が必要な理由

参照文脈なしの `chunked` は最初のトークンが最も早い（0.25〜0.74 s）が、先頭の短い部分を文脈なしで訳すため品質が落ちた。

- 見出し「Local Council Approves New Cycling Lanes」→「地方自治体、…」（一括では「市議会、…」）
- 「QUEST LOG」→ 訳されずにそのまま（一括では「クエストログ」）

後続の原文を参照文脈に入れるとどちらも一括と同じ訳になった。参照文脈の長さは 200 と 400 で品質に差がなく、
短い 200 の方が速いため 200 とした（600 では一括とほぼ同じ待ち時間になる）。

## 再現

```sh
pip install llama-cpp-python==0.3.37 "sacrebleu[ja]"
cd bench/latency
CTX=200 python bench.py plamo-3-translate-2b-Q4_K_M.gguf whole chunked_ctx
```

`FIRST`・`REST`・`CTX` 環境変数で先頭部分・以降の部分・参照文脈の大きさを変えられる（単位はコスト）。
結果は `results/` に保存される。
