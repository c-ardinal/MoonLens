# エージェント行動原則

このプロジェクトで Claude / 自動エージェントが作業する際の **思考プロセス・行動方針**。
作業手順や具体的な実装ノウハウではなく、**どう判断し、どう動くか**を定義する。
新しいセッションを開始する時はまずこのファイルを読み、原則に従って動くこと。

> 例示は過去セッションでの「思考の型」を示すためのもので、
> 同じ作業を繰り返す指示ではない。

---

## 1. 文献ベースで調査してから着手する

経験則やその場の思いつきで実装を始めない。
類似問題には大抵先行研究・古典手法があり、文献から得た方針は車輪の再発明を避けるだけでなく、
**「なぜそうするか」をユーザに説明できる根拠**になる。

手順:
1. 課題を 1-2 文で言語化する
2. WebSearch / Context7 / 論文・特許で既存手法を 2-3 件確認する
3. 採用候補をユーザに 2-3 行で要約 (どの手法 / どこで効きそうか / 既知の限界) する
4. 効果が不十分なら別手法に移り、繰り返す (「improve or move」)

**思考例**:
> 段落検出が壊れている。RLSA (Wong/Casey/Wahl 1982) と XY-cut (Nagy 1984) を確認。
> RLSA は line-spacing × 1.5 が定石だが現代の compact 文書では破綻する。
> US8565474 が左マージン基準を提案している。これを採用、効かなければ alignment 系へ進む。

---

## 2. 試行錯誤の前にプランをユーザに提示する

UI/視覚変化・大規模 refactor・破壊的変更は **2-3 行の方針** (どこを触る / 何を変えない / 想定影響)
を先に提示し、ユーザの承認を得てから着手する。

例外: 単一ファイル minor edit、ユーザが手順を明示済みの場合。

**行動例**:
> 「Phase X として A / B / C をやります。A の挙動は〜、B は〜、テストは〜。これで進めて良いですか?」

過去のインシデント:
- 同じ症状の修正を 3 回繰り返した時に user から「試行錯誤の前に文献調査を」とフィードバック
- 計画なしの実装で完成したら「期待と全然違う」と言われ巻き戻し

---

## 3. divergence を発見したら構造で塞ぐ

二経路 (production と eval、UI と CLI、A と B) で挙動が違う bug を見つけた時、
**その差分だけ局所修正してはならない**。
構造的に divergence が発生不能な形 (DI、共有 entry point、共通 adapter) に refactor する。

判断基準:
- 「ユーザの input → output 以外で 2 経路に差は無いはず」が成立しているか
- 同じバグが将来別の form で再発し得るか
- mock / golden test で divergence を catch できるか

**思考例**:
> production と eval で OCR config が違うことが 3 回目の発覚 → もう局所修正しない。
> trait 抽象化して両方を同じ pipeline に流し込む。adapter で input / output だけ差し替える。

---

## 4. SOLID / DI を遵守する

抽象 (trait / interface) に依存し、具象は外部から注入する。

特に守るもの:
- **DIP**: 高レベルポリシーが低レベル具象を直接呼ばない (capture 関数を直接呼ぶのではなく `LensInput` trait に依存)
- **SRP**: 1 関数 1 責務。orchestration と I/O と business logic を混ぜない
- **OCP**: 新 sink / 新 provider 追加が既存コードを変えないこと

**思考例 (やってはいけない)**:
> ここだけ `app.emit("...")` 直接呼ぶか → ダメ。trait 経由にすれば test も差し替えも効く。

---

## 5. 症状ではなく根本原因を直す

「○○が動かない」の修正は、その表面を黙らせるのでなく、なぜ起きるかを突き止めて構造を直す。

判断ガイド:
- 数値を上げて治ったように見える → 一時しのぎで再発する
- log / config / state を辿り、再現できる仮説に到達してから手を入れる
- 同じ症状が 2 回出たらメタ問題 (アーキ / 設定 layering / 環境差) を疑う

**思考例**:
> 翻訳が途切れる → num_predict 上げれば治る? いや、なぜ user の設定に届かないかを見る。
> deep-merge してなかった。num_predict 上げるだけでは次の bump も同じ症状になる。

---

## 6. テストファースト + 回帰防止テスト

新機能・バグ修正・refactor すべてで:
- TDD: 期待値をテストで先に表現してから実装
- バグ修正: その bug を再現する failing test を先に書く (修正で green になれば良い)
- 構造変更: 「未来の divergence」を catch する integration / golden test を追加

`AdvancedSoftwareDesign` skill (`Boundary Strategy`, `Spec Traceability` 等) の原則を尊重する。

---

## 7. 検証は段階的に行う

順序:
1. **unit test 全件 green**
2. **eval / offline harness で結果確認** (数値 + 視覚)
3. **ユーザに実機 (production) での確認を依頼**
4. ユーザの言葉で「OK」が出るまで完了と言わない

途中で詰まったら正直に「ここまで動くがここが問題」と stop して報告する。

---

## 8. 正直に報告する

うまくいかなかった事は **隠さず・婉曲化せず** 報告する。
ユーザが指摘した問題が再現するなら「再現しました」と認める。
ユーザの怒りに同調する必要はないが、**失敗を取り繕う言い訳はしない**。

**禁止フレーズ例**:
- 「概ね動いています」(動いていない部分があるなら数値で報告)
- 「微妙な regression」(回帰なら回帰と言う)
- 「ほぼ Google Lens 同等」(同等でないなら差分を出す)

---

## 9. iterate-and-measure

一発で解こうとせず、**研究 → 適用 → 計測 → 次** の loop を回す。
測れる指標 (residual chars, line count, overflow ratio, test pass count) を毎ステップ記録する。

**行動例**:
> Phase A 適用 → eval 計測 → 一部 regression → ユーザに数値で報告 → Phase B (次の手法) に移行。

---

## 10. 設定の層構造を尊重する

ユーザ設定は default を上書きするのではなく **層** として merge される。
`default.toml` の更新が既存ユーザに届く構造を維持する。
新しいキーを追加した時、既存ユーザの config が古いままでも自動で defaults を補完できるか必ず確認。

---

## 11. TaskCreate / TaskUpdate でトラッキング

3 ステップ以上の複雑な work、複数ユーザ要望が並ぶケースでは TaskCreate を使う。
完了直後に completed にする (まとめて更新しない)。
途中で blocker が出たら新 task を切って依存関係を明示する。

---

## 12. ブランチ / コミット規律

- main / master への commit / merge / push は **ユーザの明示的指示が出た時のみ**
- 「コミットして」だけでは feature branch までが暗黙のスコープ
- destructive operation (`git reset --hard`, `--force`, `--no-verify` 等) は事前承認必須
- commit は new commit を作る (`amend` は明示指示時のみ)

---

## 13. 言語使用ルール

- ユーザへの応答・報告: **日本語**
- code / comment / test name / commit message: **英語**
- 文献引用は原典の言語をそのまま (引用元の URL / paper title)

---

## 14. 大規模 refactor は段階を切る

`Phase 1`, `Phase 2`, ... と段階を区切り、各段階で:
- TaskCreate して in_progress にする
- 完了で commit-able な状態を作る
- 計測 (test count, eval metric) を記録する

「全部やってから一気に commit」はしない。途中状態でも本番が壊れないようにする。

---

## 15. 副次的なクリーンアップは別 commit で

bug 修正の commit に乗せて関係ないリファクタを混ぜない (review が困難になる)。
不要コード / dead code の cleanup は明示的に別 task / 別 commit にする。

ただし「修正のために必要な」周辺整理は同 commit でも可 (commit message に明記)。

---

## 16. 思考の補助としての例示テスト

新しいロジックを書く時、「こういうケースで何をすべきか」を test として書き下すことで
仕様が明確になる。test 自体が思考過程の memo となる (`fn xxx_in_compact_layout()` 等の命名で意図を残す)。

---

## 17. ユーザのフィードバックを次の方針に活かす

ユーザの指摘を一度聞いたら、同じ指摘を二度受けない構造を作る。
「また○○が起きた」と言われた時は、原則 1, 3, 5 のいずれかが守れていない。

過去の失敗例の中で繰り返し起きやすいパターン:
- 設定 layering を怠って既存ユーザに届かない
- production と eval で provider config が違う
- 試行錯誤で値を変えるだけで原因を見ない
- 視覚確認せず数値だけで完了報告する

これらは **原則レベルで再発防止する** ことを優先する。
